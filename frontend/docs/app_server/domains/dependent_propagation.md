# App Server Domain: dependent_propagation

## Purpose
<!-- MANUAL:BEGIN -->
Engine-hosted dependent propagation job domain: saves write only the saved object, then enqueue one durable `ArcRhoRefreshDependents` job that ArcRho Engine executes on the server host.
<!-- MANUAL:END -->

## External Interfaces
<!-- MANUAL:BEGIN -->
- Canonical contract module `python-api/src/arcrho_dependent_propagation_contract.py` owns the request/status schemas, `requests/dependent_propagation/` folder layout, reserving-class lease (5 s heartbeat, 300 s stale takeover), the status-heartbeat/staleness parameters (5 s republish, 45 s processing stale, 180 s queued stale), the live-Engine heartbeat preflight (fresh `runtime/instances/arcrho_engine/*.json` mtime within 60 s), and the `find_reserving_class_propagation_hold` write-hold probe (one lock-file stat plus a scan of the normally empty queued-requests folder).
- Engine worker `data-engine/src/arcrho_engine/dependent_propagation.py` claims the reserving-class lease, drains and merges queued requests for the same class (`merged_into` statuses), runs the canonical `calculated_dataset_service.recalculate_dependents` walk with per-tier progress, republishes the current `processing` status (primary and merged ids) every 5 s so remote pollers can tell a live slow walk from a dead worker, and retains the request file until a validated terminal status exists.
- Every save flow (DFM, Result Selection, Bornhuetter Ferguson, Cape Cod, Bootstrap, dataset sidecar/grid saves, runtime cache writes, dataset-type formula changes) preflights `require_reserving_class_writable(project, reserving_class)` before writing anything: no live Engine refuses the save with 503, and an active hold on the class (fresh lease heartbeat or a young queued request without terminal status) refuses it with 423 so one user's walk cannot race another user's edits in the same class. Unsaved work stays in the editor either way. The Excel workbook retarget (itself the `excel_link_retarget` hosted-save kind) preflights once and wraps its nested per-file saves in `suspended_reserving_class_hold_check()` so its own first enqueue does not refuse the rest, and in `deferred_save_propagation(project, class)` so those saves' roots are collected — `enqueue_save_propagation` answers `{status: "deferred"}` for that class — and walked once by the operation's `flush()` after the context exits (inline on the Engine, one queued job elsewhere); the coalescing merge remains the backstop for saves the non-atomic gate lets through together.
- Saves are Engine-hosted (`engine_hosted_save_service` client-side, `arcrho_engine/save_jobs.py` engine-side, contract `arcrho_engine_save_contract`): preflight returns its validated workspace root for the request publisher to reuse; the request file itself is the queued state, so the client does not pay for a separate queued-status write. After a 0.5 s local pickup window the client polls to a terminal status. The Engine claims by delete, holds the reserving-class lease, runs the canonical service save with the walk inline, and embeds the full response in its terminal success status. It also writes the legacy result file so an older client paired with a current Engine still works; a current client falls back to that file only when an older Engine omits the inline response. On a terminal outcome the client returns immediately and unlinks the status/result leftovers in a background thread (each unlink is an SMB round trip; the Engine's stale-artifact pruner is the backstop). At the 503 deadline, a client with no status checks whether the request file still exists: only a still-queued request is synchronously retracted; a request already removed by delete-to-claim gets the full processing timeout. `trackSavePropagation` resolves a `status: "completed"` payload immediately (no polling); the saving window then shows a notice listing `propagation.refreshed_datasets` one clickable name per row until the user dismisses it, and shows nothing when that list is empty; a clicked row asks Project Instance to open that dependent's method or dataset page. No save closes its window. Only refresh/patch flows still enqueue `ArcRhoRefreshDependents` jobs and poll them. Running inline is decided once, inside `enqueue_save_propagation`, so it covers every save path rather than only the callers that happen to use `enqueue_marked_save_propagation`; `enqueue_marked_save_propagation` consults the same flag solely to skip marking that the inline walk would immediately redo. That single decision point matters more than it looks: a queued job makes the client poll a status file it reaches over SMB, where the Windows redirector's default 10 s file/directory cache keeps serving a stale copy and hides a terminal status the Engine has already written. Dataset sidecar saves — the path Berquist Sherman commits through — queued a job for exactly that reason and waited ~15 s on a walk the Engine had finished in under a second. Project Instance polls `GET /dependent_propagation/reserving_class_busy` (~5 s) to quietly pause class-mutating actions while the class is held; there is no banner above the dataset table.
- Every hosted save and plan may instead use the no-IT Gateway configured by `%APPDATA%\ArcRho\arcrho_gateway.json`. If that local file is absent, ArcRho startup reads the shared Gateway `client_url`, probes it, and enrolls the current Windows login through a lock-protected atomic registry update; Server Connection changes retry the same process. Existing local files, including `enabled: false`, are authoritative. A failed pre-enrollment check leaves SMB selected because no HTTP request was submitted. Once enrolled, the local app server sends the same `ArcRhoHostedSave` payload over HMAC-authenticated HTTP; the machine-wide Gateway performs preflight, request publication, status observation, and cleanup on server-local disk. It persists the receipt before publication, so same-ID retries return the stored outcome and conflicting content returns 409. There is no automatic HTTP-to-SMB fallback after enrollment. Plain HTTP does not encrypt dataset or method content and is for controlled performance testing only. The supported kinds are derived from the canonical `SAVE_JOB_KINDS` registry, so every save procedure is covered; a client keeps a kind on SMB only while a deployed Gateway is old enough not to advertise it.
- Successful dependent-protocol path safety checks are cached in-process for 30 s by normalized workspace root. A workspace-root change uses a different cache key, while an inaccessible root or failed path validation invalidates that root immediately. Only successful checks enter the cache; heartbeat and reserving-class hold checks still run for every save.
- Each hosted save or plan appends one structured client-side timing record to `%LOCALAPPDATA%\ArcRho\logs\client_save_latency.jsonl` (`Arcode` replaces `ArcRho` in Arcode mode). The record identifies `transport` as `smb` or `http_gateway`; Gateway records include capability time, HTTP round-trip time, attempts, and `result_source: http_gateway`, while SMB records retain detailed share timings and cleanup correlation. Payloads and method data are never logged, and logging remains best-effort.
- Saves are one-step from the UI: hitting Save commits directly, with no dependent-update preview or confirmation dialog (the two-step plan/confirm flow was removed 2026-08-14; unsaved work still stays in the editor on any refusal). The server-side plan machinery remains in place but currently has no UI caller: every save endpoint keeps its sibling `<save path>/plan` (`Mode: "plan"` in the same hosted-save contract) that runs `save_plan_service.build_save_plan` on the Engine — it resolves the save's propagation roots through `save_propagation_roots` in the module that owns the save, unions the sidecar `Dependents` closure with the dataset-type formula closure, answers with the reachable objects plus a `fingerprint` of everything it read, writes nothing, and takes no reserving-class lease. A commit carrying `plan_fingerprint` still gets the under-lease recheck and a 409 (`SAVE_PLAN_STALE_MESSAGE`) when the class moved; a commit without one (all current UI saves) skips the recheck.
- Both Engine-executed flows act as the user who submitted them, because Engine instances run under their own service profiles and any instance may claim any request. A hosted save carries `UserName` (the submitter's Windows login) plus `UserDisplayName` (that login already resolved by the submitting app server against the workspace username index); a propagation request carries `UserName` only and the Engine resolves it. Both bind `user_identity_service.acting_identity(...)` around the work, so the sidecars written by the save and by the walk — and the `index.json` rows projected from them — name the person who made the edit. `UserDisplayName` is an additive field: a request without it still identifies its user by login. See the user_identity domain.
- Server-host in-process producers (ResQ migration, public Python API) keep walking in-process but hold the same reserving-class lease.
- Because the job is the sole propagation writer, the dataset open fast path trusts sidecar status + index folder signature (see the arcrho domain), and open windows watch their object for job or other-user rewrites through the object_change_watch domain's stat-only fingerprint endpoint.

## Data/State/Caches
<!-- MANUAL:BEGIN -->
- Two lease scopes share the `locks` folder. A reserving-class lease is keyed by project + class; a project-scope lease (`project-<digest>.lock`) is keyed by project alone and is taken by a job that rewrites what every class derives from -- currently the dataset-type change job. While a project-scope lease is fresh, `find_reserving_class_propagation_hold` answers `{"reason": "project"}` for every class of that project, until the job narrows it: `narrow_project_scope_lease` rewrites the lease file with a `classes` list (owner token and heartbeat unchanged), after which the per-class probe answers `project` only for the listed classes and reads the lease payload to find out -- one extra read, paid only while a project lock is fresh. `find_project_scope_propagation_hold` ignores the list: the job is still running, so another project-scope job still may not start.
- Both are answered by one directory listing rather than one stat per question, because a preflight on a mapped drive pays per operation. `find_any_reserving_class_propagation_hold` uses the same listing to answer the whole-project question a project-scope job must ask before it starts, and names the class it found.
- The project-scope lease is recovered far later than a class lease (`PROJECT_SCOPE_LEASE_STALE_SECONDS`, 900 s): the job it protects can legitimately spend longer in one stage than any single class walk takes.
- Transient runtime files under `<server-root>/requests/dependent_propagation/{requests,statuses,locks}`; statuses follow the project-duplication retention policy (retained, no automatic pruning).
- Hosted-save requests live directly under `<server-root>/requests`; statuses and legacy compatibility results live under `<server-root>/requests/save_jobs/{statuses,results}` until the client consumes them or the Engine prunes stale artifacts.
- HTTP pilot receipts live under `<server-root>/runtime/arcrho_gateway/receipts`; terminal receipts are retained for 24 hours by default, while nonterminal receipts are preserved for recovery.
- Machine-local diagnostic records under `%LOCALAPPDATA%\ArcRho\logs\client_save_latency.jsonl`, plus at most three numbered rotated backups. These files never live in the ArcRho Server workspace.
- Save responses carry `propagation: {job_id, status: "queued"}`, or `{status: "unchanged"}` for no-op saves whose publication revision did not change; a save nested inside a `deferred_save_propagation` operation reports `{status: "deferred"}` and the operation's own response carries the flushed walk.
- Server-side walk diary at `<server-root>/runtime/logs/dependent_propagation.log`, written by the Engine worker through the shared `arcrho_engine.runtime_log` appender (UTC stamps, 1 MB rotation to `.1`, every error swallowed). The Engine is packaged `--noconsole`, so this file is the only durable account of a walk: a status file keeps just the newest progress snapshot, which means a phase that stalls otherwise leaves nothing behind but file timestamps. Each job logs its queue wait and claim (including a claim missed because the class was busy, which is otherwise indistinguishable from a slow walk), the closure-marking outcome, one line per stage transition carrying the elapsed time of the stage that just ended, and a terminal line with the held duration plus the per-bucket dataset names and unredacted failure reasons that the client-facing status message deliberately truncates. Timing a stage on its transition is what localizes a stall: a walk that spends 15 s in one phase names that phase instead of reporting one total. The same appender backs `hosted_saves.log` and `project_duplication.log`, so all three share one rotation and never-raises guarantee.
<!-- MANUAL:END -->

## Common Change Tasks
<!-- MANUAL:BEGIN -->
1. Change the job contract: update the canonical contract module first, then the Engine worker, app-server service, UI poller, and tests together.
2. Add a propagation-triggering save flow: preflight the Engine, mark the first reachable method tier review-needed (`refresh_method_statuses_for_dependents(..., direct_only=True)` — the Engine job re-marks the full closure on claim), then `enqueue_save_propagation`; never run the walk or the deep closure marking inline on a client.
3. Add a hosted-save kind: register it in `SAVE_JOB_KINDS`, give its service a `save_propagation_roots` that mirrors how the save derives its roots (the plan resolves them through that one function, so the two cannot drift), and add the `/plan` route beside the save route with one shared argument projection. The UI saves in one step and does not call the plan endpoint.
<!-- MANUAL:END -->

## Known Risks
<!-- MANUAL:BEGIN -->
- Failed jobs are not auto-retried: downstream methods stay Review Needed until the next save or manual refresh re-enqueues a walk.
- A failed job raises no warning status line in the UI (owner decision, 2026-08-07): the dataset table's review-needed flags are the failure surface. `trackSavePropagation` fires `onComplete` at any terminal outcome (`result` null on failure) so the table refresh always runs after the walk finalized downstream statuses. The save popup treats the null resolution as "not clean" and leaves the window open instead of closing it.
- A plain filesystem cannot atomically fence the stale-lease takeover race; the generous thresholds make it acceptable (same residual gap as project duplication). The same non-atomicity applies to the reserving-class write hold: two saves may pass the preflight together, and the Engine's claim-time merge keeps that safe.
- The write hold is freshness-bounded on purpose: a dead worker's lease stops being renewed and the hold clears after 45 s; an abandoned queued request stops holding after 180 s. Clients never delete locks — only the Engine's stale takeover reclaims them.
- The UI poller treats a `processing` status whose signature stops moving for 45 s (or a `queued` one for 180 s) as stalled; the popup closes with the window left open.
- The plan endpoints and the commit-time fingerprint recheck are currently dormant (no UI caller sends `plan_fingerprint`); a save that races another user's change in the same class is caught by the existing `expected_revision` conflicts and the reserving-class hold, not by a reviewed plan.
