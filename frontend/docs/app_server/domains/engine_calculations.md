# App Server Domain: Engine Calculations (Server-Hosted Transport)

## Purpose
<!-- MANUAL:BEGIN -->
Run the legacy ArcRho Engine calculation exchange — publish one `request-*.json` into the workspace `requests` root and wait for the CSV the Engine writes — and the whole dataset run built around it on the ArcRho Server host over HTTP instead of over the mapped drive. This is a transport around the unchanged `ArcRhoTri` / `ArcRhoVec` / `ArcRhoHeaders` file contract and the unchanged `arcrho_runtime_service` routes: the Engine still claims the same request file and writes the same CSV to the same location, and the cache validation, sidecar write, dependent enqueue, and index refresh are the same service code; only the process that runs them moves from the Client PC to the machine-wide ArcRho Gateway, where every step is a local-disk operation.
<!-- MANUAL:END -->

## Entry Points
<!-- MANUAL:BEGIN -->
No new browser-facing route. Three operations share one Gateway route:

| Operation | Client entry | Service run on the host |
| --- | --- | --- |
| `dataset_run` | `POST /arcrho/tri`, `/arcrho/tri/refresh`, `/arcrho/vec`, `/arcrho/vec/refresh` via `engine_calculation_service.run_hosted_dataset_operation` | `arcrho_runtime_service.run_arcrho_tri` (options `force_refresh`, `local_only`, `allow_derived`, `write_sidecar`, `temporary_session_id`) |
| `dataset_precheck` | `POST /arcrho/tri/precheck`, `/arcrho/vec/precheck` via the same client function | `arcrho_runtime_service.arcrho_precheck` (options `local_only`, `allow_derived`, `temporary_session_id`, `allow_runtime_cache_provenance`) |
| `exchange` | every remaining `arcrho_runtime_service` request site — header-cache requests (`/arcrho/headers`, dataset label hydration), Result Selection source loads, calculated-dataset input materialization, and the exchanges inside a run that itself executes locally — via `engine_calculation_service.run_engine_calculation(pairs, data_path, timeout_sec)`, which returns `ok`, `status` (`completed` / `timeout` / `gateway_error`), `request_file`, `transport`, and an optional `message` | `engine_calculation_service.publish_and_wait` |

Gateway side: `POST /api/engine-calculations` (`arcrho_engine_calculation_contract.ENGINE_CALCULATION_PATH`), authenticated with the same per-user HMAC headers as hosted saves and workspace reads. `GET /api/capabilities` advertises `engine_calculation_functions` and `engine_calculation_operations`; a client facing an older gateway that lists only `exchange` keeps the dataset routes local.
<!-- MANUAL:END -->

## Key Files
<!-- MANUAL:BEGIN -->
- `python-api/src/arcrho_engine_calculation_contract.py` - The canonical `ENGINE_CALCULATION_KINDS` registry (Engine function → exact request-file keys the Engine reads, whether a reserving class is named, allowed output variants and operations), the `OPERATION_OPTIONS` table (each operation's option names and types), server-owned keys a client may never send (`DataPath`, `StatusPath`, `RequestId`, `UserName`), request validation, wait clamping, route path, and the exchange response shape.
- `app_server/helpers.py` - `build_engine_request_info` (the `key = value#...` request line), `send_request_like_vba` (publishes into `config.REQUEST_DIR` and stamps the acting user), `wait_for_file` (local file-event wait, or probe-and-poll on a network drive), `is_network_path`.
- `app_server/services/engine_calculation_service.py` - `publish_and_wait` (the exchange itself, identical on both hosts), `execute_hosted_engine_calculation` (the server-side entry: derives the output path with `set_data_path_like_vba` — or the Temporary view path for `OutputVariant: temporary_view` — then publishes and waits, or delegates a dataset operation to `arcrho_runtime_service`), `run_engine_calculation` (client transport for one exchange: capability probe, request signing, result-visibility wait, diagnostics record), and `run_hosted_dataset_operation` (client transport for a dataset run/precheck: same selection, response returned verbatim with rebased paths, dataset handle registration, `504` after acceptance).
- `app_server/api/arcrho_router.py` - The `/arcrho/tri*` and `/arcrho/vec*` routes build the pairs and options once and hand them to `run_hosted_dataset_operation` with the local service call as the fallback.
- `app_server/services/workspace_read_client.py` - `post_signed_json`, `GatewayTransportFailure`, `cached_gateway_capabilities`, and `rebase_workspace_paths`, shared with workspace reads.
- `data-engine/src/arcrho_gateway/engine_calculations.py` - Server-side executor: authenticates, validates against the contract, imports the canonical executor named by `EXECUTOR_MODULE` / `EXECUTOR_FUNCTION`, runs it under `acting_identity`, and maps a service `HTTPException` to the same status.
- `data-engine/src/arcrho_gateway/main.py` - Route dispatch (shared with workspace reads) and the capability field.
- `data-engine/src/arcrho_gateway/build_exe.py` - Bundles the contract, the executor module, and `watchdog` so the server-side wait is a file-system event.
<!-- MANUAL:END -->

## Data/State/Caches
<!-- MANUAL:BEGIN -->
- Transport selection, per request: the output CSV must be on a UNC or mapped network drive (`is_network_path`; a local workspace waits on a local file event and gains nothing remotely), the process must not run with `ARCRHO_RUNTIME_SERVER_ROOT` set (Engine, Bridge, Gateway publish locally), the local `%APPDATA%\ArcRho\arcrho_gateway.json` credential must be enabled, the gateway's `/api/capabilities` (cached 30 s on success, 10 s on failure) must list the Engine function, and the request must validate against the contract (`request_not_hostable` otherwise). Any other outcome runs `publish_and_wait` locally exactly as before.
- Request: only the legacy request-file keys travel, as ordered `[key, value]` string pairs (order is part of the request — the header cache file name is derived from pair values in order), plus `TimeoutSeconds` (clamped to 0.1–300 s; for a dataset run this is the per-exchange Engine budget, `config.ENGINE_REQUEST_TIMEOUT_SEC`), `Operation` (`exchange` by default), its `Options` (validated against `OPERATION_OPTIONS`: booleans, and a UUID-or-null `temporary_session_id`), an optional `OutputVariant` for the exchange (`canonical` or, for dataset functions, `temporary_view`), and the enrolled `UserName` / display name. The server derives `DataPath` itself and stamps `UserName` from the acting identity, so a client can neither name an arbitrary output file nor act as another user. Key spellings are exact (`periodType`), because the Engine reads keys verbatim.
- Exchange response: `ok`, `status` (`completed` / `timeout`), the server's `data_path` and `request_file`, and `wait_ms`. The client rebases the server paths onto its own root and refuses (500) a `data_path` that differs from the one it computed, then waits for the CSV to become visible on its own drive through `wait_for_file` — the same probe write that defeats the SMB redirector's cached "not found" — for at most `ENGINE_OUTPUT_VISIBILITY_TIMEOUT_SECONDS`, reporting a `timeout` with an explanatory message otherwise.
- Dataset run / precheck response: the service's own response, verbatim (`ok`, `status`, `need_request`, `ds_id`, `data_path`, `request_file`, `calculated_updates`, `sidecar_written`, …), with every server-rooted path rebased onto the client's root. A successful `dataset_run` registers `ds_id` → rebased `data_path` locally through `dataset_service.register_dataset_handle`, exactly as the local route registers it, so the id-addressed `GET /dataset/{id}` and grid routes keep resolving. On the server the run executes with the Temporary view, sidecar, dependent-propagation enqueue, index refresh, and lock semantics unchanged; the exchanges inside it are local because the run is a server process.
- Fallback rule: a gateway-layer failure before the request could have been acted on (unreachable, authentication or validation refusal without the `X-ArcRho-Workspace-Root` header, an older gateway without the route or the operation) falls back to the local exchange or local route. Once the request may have been accepted — a timeout waiting for the answer, a dropped connection or invalid body after the server answered — an exchange reports `timeout` / `gateway_error` with `message`, and a dataset operation raises `504` (`Reload the dataset before retrying`); neither is retried over SMB, because a second request makes the Engine compute the same CSV twice and a second run would repeat the sidecar and dependent work. A refusal raised by the hosted service itself (a project the server cannot find, `423` on a locked cache, `422` on a bad session id) passes through as the same `HTTPException`.
- No receipt: a calculation is a deterministic function of the workspace, so the transport keeps no idempotency receipt; the caller's own retry is a fresh request.
- Identity: `send_request_like_vba` stamps `UserName` from `user_identity_service.get_windows_login_name()`, which answers with the acting identity when the Gateway publishes on a user's behalf; the sidecar the client writes afterwards still carries that user's display name.
- Diagnostics: one record per request in `client_read_latency.jsonl` with `read_kind: engine_calculation`, `engine_function`, `operation` (dataset operations), `transport` (`http_gateway` or `smb`), `reason` when local (`local_path`, `server_process`, `gateway_disabled`, `gateway_config_invalid`, `gateway_unreachable`, `function_not_advertised`, `operation_not_advertised`, `request_not_hostable`, `gateway_rejected:<code>`), `outcome`, `total_ms`, `remote_ms`, `server_wait_ms` (exchange), `http_status`, and the logical project/class/object names — never payload data.
<!-- MANUAL:END -->

## Common Change Tasks
<!-- MANUAL:BEGIN -->
1. Host another Engine function: add one `EngineCalculationKind` entry naming the exact request-file keys its handler reads; the Gateway advertises it on the next deploy and the client routes it the moment the capability appears. Keep `set_data_path_like_vba` able to derive its output path.
2. A request site that targets a different output location than the canonical cache must name it as an `OutputVariant` the contract knows and `resolve_engine_output_path` can derive; the client never sends a path.
3. Host another route: add an operation and its option table to the contract, dispatch it in `execute_hosted_engine_calculation` to the canonical service function, and wrap the route in `run_hosted_dataset_operation` with the local call as fallback; the Gateway advertises the operation on the next deploy.
4. Rebuild and redeploy the Gateway after any change here; the Engine and Bridge bundle `app_server` too and follow their own deployment rules.
<!-- MANUAL:END -->

## Known Risks
<!-- MANUAL:BEGIN -->
- Each hosted calculation holds one gateway handler thread for the whole wait (up to the clamped timeout); the gateway has no concurrency cap yet, so a burst of long calculations competes with hosted saves and reads in the same process.
- Direct service callers of `run_arcrho_tri` outside the `/arcrho/*` routes (Result Selection source materialization, calculated-dataset input recursion when the outer run is local) still perform the cache validation, sidecar write, dependent enqueue, and index refresh over the mapped drive; only their exchanges are hosted. `GET /dataset/{id}` after a run still reads the CSV and header caches over the mapped drive.
- A hosted `dataset_run` holds `reserving_class_io_lock` inside the Gateway process, so concurrent runs from different Client PCs against one reserving class serialize there — stricter than the per-process lock each client held before, and intended.
- A gateway timeout leaves the request file in the server's `requests` root until the Engine claims it or the Orchestrator's five-minute garbage collection removes it, exactly as a client-published timeout does today.
