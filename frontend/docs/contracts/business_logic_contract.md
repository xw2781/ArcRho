# Business Logic Contract

## Purpose
Set lightweight app-server and domain behavior guardrails for the current pre-production app.

Prefer clean coordinated refactors over compatibility shims unless the user explicitly asks for migration support.

## Scope
This contract applies when changing app-server routes, schemas, services, runtime path config, workflow persistence, project settings persistence, cache/refresh behavior, reserving-class data, dataset behavior, or frontend consumers that depend on those contracts.

## Core Rules
1. Keep domain logic layered: routers handle transport/validation, schemas define request shapes, and services own persistence and business logic.
2. Change route paths, request/response shapes, saved file schemas, and cache semantics only as coordinated refactors. Update all known producers, consumers, docs, and generated indexes in the same change.
3. Keep `workspace_paths.json` and `app_server/config.py` as the single source for workspace paths. Do not duplicate path derivation in services. `arcrho_api/config.py` owns ArcRho Server root resolution itself -- the config file name, the `%APPDATA%\ArcRho` folder, the `ARCRHO_SERVER_ROOT`/`ARCRHO_RUNTIME_SERVER_ROOT` overrides, and the packaged default root -- so the app server, the Python API, and macros always resolve the same workspace; `app_server/config.py` reads those constants and helpers instead of redefining them, and adds only the Arcode-mode AppData branch and the `paths` normalization it owns.
4. Preserve data integrity for filesystem-backed operations. Project settings, workflow files, caches, and audit logs should fail clearly rather than silently diverging or corrupting state.
5. Keep API validation and status behavior explicit. Input problems should not become generic `500` responses, and lock/contention cases should remain distinguishable.
6. Keep refresh/cache side effects visible in route behavior and docs when they matter to users or downstream features.
7. Keep generated-dataset behavior canonical across the frontend and ResQ migration. Both producers must delegate `Generated=true` single-instance datasets to ArcRho Engine and build the persisted engine sidecar through `arcrho_api.engine_dataset_sidecar_contract`; migration must not copy ResQ axis labels, counts, formulas, users, or timestamps into that sidecar. Cached reads hydrate Dataset Type formulas from `dataset_types.json` and missing development labels from the canonical project-header contract before first render, never from a generic `12, 24, ...` fallback. Keep dataset number-format defaults in the workspace-global `config/dataset_number_formats.json`; both producers resolve the same fallback and Dataset Type Name overrides across all reserving-class paths.
8. Keep current Result Selection method JSON self-contained. A valid v2 open reads only its own method JSON and output sidecar; source values, weights, native origin lengths, all configured Ratio Basis vectors, calculated/final ultimates, and overrides come from the method JSON. Durable precedent saves refresh registered RS artifacts through the shared review lifecycle in rule 12. Saving a review-needed RS must revalidate and refresh exactly the revised incoming precedent list so removed stale dependencies do not block recovery. Missing or unreadable precedents remain blocking; review-needed precedents are returned as a non-blocking save warning. Only an exact v1 marker may take the one-time dependency-reading upgrade path.
9. Keep current DFM method JSON self-contained. A valid v2 open reads only `DFM@<method name>.json` and the declared output dataset sidecar; the input triangle snapshot, Ratio Basis snapshot, calculated ratios and averages, selected ultimate vector, display metadata, and source revisions come from the method JSON. An ordinary Save trusts those embedded snapshots and must not reopen precedents merely to validate duplicate labels. ArcRho-managed precedent saves refresh affected DFM-derived state before calculated and Result Selection descendants, while preserving DFM-owned selections, formulas, stored Excel results, notes, and the method-owned origin/development axes. Refresh maps source CSV geometry to those axes and must not require duplicate label arrays from precedent sidecars. Failed refreshes preserve the last valid publication. Only an exact v1 marker may read its precedents for a transactional one-time upgrade.
10. Keep current Bornhuetter Ferguson and Cape Cod method JSON self-contained. A valid open reads only the method JSON (`BF@<method name>.json` v3, `CC@<method name>.json` v1) and its output dataset sidecar; every source, parameter, origin-label, calculated, output, and display snapshot comes from the method JSON. An ordinary Save trusts those embedded snapshots and must not reopen precedents merely to validate duplicate labels. ArcRho-managed precedent saves refresh affected artifacts by mapping source CSV rows onto the method-owned origin axis, without requiring precedent-sidecar label arrays, while preserving method-owned weights, parameters, and formatting; they then apply the shared review lifecycle in rule 12. Failed refreshes preserve the last valid publication. Earlier formats are unsupported and must be re-imported from their canonical source. Cape Cod calculations are owned by `arcrho_api/cape_cod_contract.py`; every producer (app server, frontend mirror, migration) must delegate to it, and its formulas must remain the ResQ-verified Generalised Cape Cod calculation documented in `docs/plans/cape_cod_method_plan.md`.
11. Preserve ResQ review status during method import. Vector-backed methods (DFM, Bornhuetter Ferguson, Cape Cod, and Result Selection) read `OutputVector.Status`; Berquist-Sherman methods read `OutputTriangle.Status`. Normalize ResQ `0` to OK and `2` to Needs Review, then retain Needs Review when either the imported output requests review or ArcRho finds a newer precedent.
12. Treat a method output sidecar's `status` as a human-review acknowledgement, never as the success flag for automatic refresh. Every explicit Save, including a no-op Save, sets the saved method output to `0`, refreshes all reachable downstream data, and then sets every reachable method-backed output to `2` until that method is explicitly saved. A method Save must not be blocked solely because one or more readable method-backed precedents remain at `2`; the save response returns their canonical unique names/count and the method window shows a page-local warning after the save commits. Refresh or Sync alone must not clear an existing review alert. Plain input and app-calculated datasets, including formula vectors between two methods, remain `0`; the dependency walk must still traverse through them so later method-backed outputs are alerted. Report calculation, propagation, and index failures separately from review status, and never present a committed upstream save with a failed downstream refresh as an unqualified success.
13. Keep the project-owned imported table the only raw source anything reads. Every project owns `<project>/source/master_table.csv`, written by exactly one owner (`source_table_service`) from exactly one configured import source. App-server readers resolve it through `source_table_service`, and the data engine resolves it from the project folder alone; no consumer may read `field_mapping.json::table_path`, a SQL Server table, or any other external location for data. `table_path` and the SQL Server profile are import sources only. A `csv` project re-copies automatically when the external file's identity changes, and a transient read failure preserves the last good import instead of persisting a degraded one; an `mssql` project is never re-read without an explicit user import. `arcrho_api/source_table_contract.py` owns the layout, the `source_import.json` schema, normalization, and the staleness rule; a component that cannot import it must mirror it under a parity test. The project-shared import profile must never persist credentials.
14. Keep project-folder duplication server-hosted, resumable, and location-independent. Project Settings submits the canonical versioned `ArcRhoDuplicateProject` request using logical source/target names plus a validated server-root-relative projects-directory setting; ArcRho Engine derives absolute paths from its own server root, uses the fixed `<server-root>/requests` duplication protocol, copies into a same-parent staging folder, excludes canonical transient data-root folders, publishes atomic progress/terminal status, and exposes the target only after the complete copy succeeds. The client must not traverse or copy the source project over its mapped/UNC connection, and it must not persist the folder-tree mapping or duplicated project row before Engine reports success. Generate and persist a safe request ID before POST, bind it to one location-independent canonical server receipt, and replay that same ID after uncertain responses without resetting processing or terminal Engine status. Scope local recovery by the normalized workspace root and configured projects/request subpaths. Fingerprint the ordered Project Map headers together with the submission-time source row, use the same-page ephemeral snapshot, and block reload finalization if the source metadata changed or disappeared. If a target row already exists during recovery, reconstruct its source-name form and require the same fingerprint before treating metadata as finalized. Make post-success metadata writes idempotent, and never delete an Engine-published target when polling or metadata finalization is uncertain.

## Before Finishing
1. State which business-logic area changed, or state "no business-logic impact."
2. Update affected MANUAL sections in `docs/app_server/*.md`, `docs/app_server/domains/*.md`, or `docs/runtime/*.md` when behavior changes.
3. Run `python tools/docs_index_builder.py --write`.
4. Run `python tools/docs_index_builder.py --check`.
