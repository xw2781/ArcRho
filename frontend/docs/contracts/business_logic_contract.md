# Business Logic Contract

## Purpose
Set lightweight app-server and domain behavior guardrails for the current pre-production app.

Prefer clean coordinated refactors over compatibility shims unless the user explicitly asks for migration support.

## Scope
This contract applies when changing app-server routes, schemas, services, runtime path config, workflow persistence, project settings persistence, cache/refresh behavior, reserving-class data, dataset behavior, or frontend consumers that depend on those contracts.

## Core Rules
1. Keep domain logic layered: routers handle transport/validation, schemas define request shapes, and services own persistence and business logic.
2. Change route paths, request/response shapes, saved file schemas, and cache semantics only as coordinated refactors. Update all known producers, consumers, docs, and generated indexes in the same change.
3. Keep `workspace_paths.json` and `app_server/config.py` as the single source for workspace paths. Do not duplicate path derivation in services. `arcrho_api/config.py` owns ArcRho Server root resolution itself -- the config file name, the `%APPDATA%\ArcRho` folder, the `ARCRHO_SERVER_ROOT`/`ARCRHO_RUNTIME_SERVER_ROOT` overrides, and the packaged default root -- so the app server, the Python API, and macros always resolve the same workspace; `app_server/config.py` reads those constants and helpers instead of redefining them, and adds only the Arcode-mode AppData branch and the `paths` normalization it owns.
4. Preserve data integrity for filesystem-backed operations. Project settings, workflow files, caches, and audit logs should fail clearly rather than silently diverging or corrupting state.
5. Keep API validation and status behavior explicit. Input problems should not become generic `500` responses, and lock/contention cases should remain distinguishable.
6. Keep refresh/cache side effects visible in route behavior and docs when they matter to users or downstream features.
7. Keep generated-dataset behavior canonical across the frontend and ResQ migration. Both producers must delegate `Generated=true` single-instance datasets to ArcRho Engine and build the persisted engine sidecar through `arcrho_api.engine_dataset_sidecar_contract`; migration must not copy ResQ axis labels, counts, formulas, users, or timestamps into that sidecar. Cached reads hydrate Dataset Type formulas from `dataset_types.json` and missing development labels from the canonical project-header contract before first render, never from a generic `12, 24, ...` fallback. Keep dataset number-format defaults in the workspace-global `config/dataset_number_formats.json`; both producers resolve the same fallback and Dataset Type Name overrides across all reserving-class paths.
8. Keep current Result Selection method JSON self-contained. A valid v2 open reads only its own method JSON and output sidecar; source values, weights, native origin lengths, all configured Ratio Basis vectors, calculated/final ultimates, and overrides come from the method JSON. Durable precedent saves refresh registered RS artifacts through the shared review lifecycle in rule 12. Saving a review-needed RS must revalidate and refresh exactly the revised incoming precedent list so removed stale dependencies do not block recovery. Missing or unreadable precedents remain blocking; review-needed precedents are returned as a non-blocking save warning. Only an exact v1 marker may take the one-time dependency-reading upgrade path.
9. Keep current DFM method JSON self-contained. A valid v2 open reads `DFM@<method name>.json` and the declared output dataset sidecar; the input triangle snapshot, Ratio Basis snapshot, calculated ratios and averages, selected ultimate vector, display metadata (including resolved dataset-reference axis labels), and source revisions come from the method JSON. Ratios User Entry datasets parsed from authoritative `inputs` are graph precedents alongside Input Triangle and Ratio Basis, while `display inputs` remain presentation-only. Saving a dataset referenced by an authoritative Ratios User Entry formula refreshes each dependent DFM through the Engine dependent-propagation walk: the walk re-resolves the dataset references, re-evaluates the affected User Entry values, republishes the method JSON and outputs, and marks the output Review Needed; a blank or non-numeric referenced cell aborts that refresh and preserves the last valid publication. An opened DFM always shows its persisted values and stays clean; opening resolves dataset references only to warm the in-session evaluation cache used after ratio edits. An ordinary Save trusts embedded snapshots and must not reopen precedents merely to validate duplicate labels. ArcRho-managed precedent saves refresh affected DFM-derived state before calculated and Result Selection descendants, while preserving DFM-owned selections, formulas, stored Excel-linked results, notes, and the method-owned origin/development axes; dataset-referenced User Entry values are re-resolved by that refresh rather than preserved. Refresh maps source CSV geometry to those axes and must not require duplicate label arrays from precedent sidecars. Failed refreshes preserve the last valid publication. Only an exact v1 marker may read its precedents for a transactional one-time upgrade.
10. Keep current Bornhuetter Ferguson and Cape Cod method JSON self-contained. A valid open reads only the method JSON (`BF@<method name>.json` v3, `CC@<method name>.json` v1) and its output dataset sidecar; every source, parameter, origin-label, calculated, output, and display snapshot comes from the method JSON. An ordinary Save trusts those embedded snapshots and must not reopen precedents merely to validate duplicate labels. ArcRho-managed precedent saves refresh affected artifacts by mapping source CSV rows onto the method-owned origin axis, without requiring precedent-sidecar label arrays, while preserving method-owned weights, parameters, and formatting; they then apply the shared review lifecycle in rule 12. Failed refreshes preserve the last valid publication. Earlier formats are unsupported and must be re-imported from their canonical source. Cape Cod calculations are owned by `arcrho_api/cape_cod_contract.py`; every producer (app server, frontend mirror, migration) must delegate to it, and its formulas must remain the ResQ-verified Generalised Cape Cod calculation documented in `docs/plans/cape_cod_method_plan.md`. Bornhuetter Ferguson and Cape Cod share the Bootstrap exception for one precedent each: the percentage developed a method applies belongs to the selected development factors of the DFM behind its Development Pattern (BF) or Prior Ultimate (Cape Cod) source, never to a ratio against Latest, which is undefined for an origin whose latest observation is zero. That vector is projected from the DFM method JSON through `arcrho_api.dfm_contract.dfm_percent_developed_vector` while the dependency graph edge stays registered against the dataset the DFM publishes, and it is embedded as a source snapshot -- `percentage_developed` for BF, `prior_ultimate_percentage_developed` for Cape Cod -- covered by that precedent's source revision so a changed factor selection invalidates it even when the published ultimates do not move. A Cape Cod prior ultimate with no DFM behind it carries no pattern and is the only case that still falls back to `Latest / Prior Ultimate`. A ResQ import cannot reach the ArcRho DFM, so it copies that snapshot from the per-origin `PercentageDevelopedValues(i)` the ResQ BF or Cape Cod method exposes (ResQ's own factor-based figure under its DFM settings) rather than deriving a ratio; a method that exposes none lands the ratio (BF) or no pattern (Cape Cod), and strict extraction refuses it. The same rule covers `BST@<method name>.json` v1 with two Bootstrap-specific additions: its first precedent is a DFM **method** rather than a dataset, so the embedded snapshot is projected from the DFM method JSON while the dependency graph edge is registered against the dataset that DFM publishes; and simulated reserves are never persisted, so a stored seed plus `simulation_count` must reproduce the stored `simulation_summary` bit for bit on reopen and a drift must be reported rather than silently accepted. Bootstrap calculations are owned by `arcrho_api/bootstrap_contract.py` and `arcrho_api/bootstrap_simulation.py`, documented in `docs/plans/bootstrap_method_plan.md`.
11. Preserve ResQ review status during method import. Vector-backed methods (DFM, Bornhuetter Ferguson, Cape Cod, Bootstrap, and Result Selection) read `OutputVector.Status`; Berquist-Sherman methods read `OutputTriangle.Status`. Normalize ResQ `0` to OK and `2` to Needs Review, then retain Needs Review when either the imported output requests review or ArcRho finds a newer precedent.
12. Treat a method output sidecar's `status` as a human-review acknowledgement, never as the success flag for automatic refresh. Every explicit Save sets the saved method output to `0`. A Save whose publication revision changed marks every reachable method-backed output `2` before returning and enqueues the Engine propagation job that refreshes all reachable downstream data; the walk finalizes those outputs at `2` until each method is explicitly saved. A no-op Save (publication revision unchanged) sets its own output to `0` and submits no job, leaving downstream statuses untouched. A method Save must not be blocked solely because one or more readable method-backed precedents remain at `2`; the save response returns their canonical unique names/count and the method window shows a page-local warning after the save commits. Refresh or Sync alone must not clear an existing review alert. Plain input and app-calculated datasets, including formula vectors between two methods, remain `0`; the dependency walk must still traverse through them so later method-backed outputs are alerted. Report calculation, propagation, and index failures separately from review status, and never present a committed upstream save with a failed downstream refresh as an unqualified success.
13. Keep the project-owned imported table the only raw source anything reads. Every project owns `<project>/source/master_table.csv`, written by exactly one owner (`source_table_service`) from exactly one configured import source. App-server readers resolve it through `source_table_service`, and the data engine resolves it from the project folder alone; no consumer may read `field_mapping.json::table_path`, a SQL Server table, or any other external location for data. `table_path` and the SQL Server profile are import sources only. A `csv` project re-copies automatically when the external file's identity changes, and a transient read failure preserves the last good import instead of persisting a degraded one; an `mssql` project is never re-read without an explicit user import. `arcrho_api/source_table_contract.py` owns the layout, the `source_import.json` schema, normalization, and the staleness rule; a component that cannot import it must mirror it under a parity test. The project-shared import profile must never persist credentials.
14. Keep project-folder duplication server-hosted, resumable, and location-independent. Project Settings submits the canonical versioned `ArcRhoDuplicateProject` request using logical source/target names plus a validated server-root-relative projects-directory setting; ArcRho Engine derives absolute paths from its own server root, uses the fixed `<server-root>/requests` duplication protocol, copies into a same-parent staging folder, excludes canonical transient data-root folders, publishes atomic progress/terminal status, and exposes the target only after the complete copy succeeds. The client must not traverse or copy the source project over its mapped/UNC connection, and it must not persist the folder-tree mapping or duplicated project row before Engine reports success. Generate and persist a safe request ID before POST, bind it to one location-independent canonical server receipt, and replay that same ID after uncertain responses without resetting processing or terminal Engine status. Scope local recovery by the normalized workspace root and configured projects/request subpaths. Fingerprint the ordered Project Map headers together with the submission-time source row, use the same-page ephemeral snapshot, and block reload finalization if the source metadata changed or disappeared. If a target row already exists during recovery, reconstruct its source-name form and require the same fingerprint before treating metadata as finalized. Make post-success metadata writes idempotent, and never delete an Engine-published target when polling or metadata finalization is uncertain.

15. Keep dependent propagation Engine-hosted, durable, and location-independent. The save endpoints themselves are Engine-hosted: a Client PC pays ~0.4 s per file operation over the mapped drive, so the six save endpoints (DFM, Result Selection, Bornhuetter-Ferguson, Cape Cod, Bootstrap, dataset sidecar) ship the whole save to ArcRho Engine through the allowlisted `ArcRhoHostedSave` contract (`arcrho_engine_save_contract`) — the request file itself as queued state in the requests root for instant watchdog pickup, delete-to-claim, a 0.5 s initial client polling delay, the canonical `app_server` service save executed under the reserving-class lease with the dependent walk run inline (`inline_engine_propagation`; the walk finalizes every status, and walk failures report in the payload, never as an HTTP error after a committed save), and the service's full response embedded in the terminal success status so current clients avoid a second result read. The Engine also writes the legacy result file for mixed-version clients, preserving exact endpoint shapes and error codes (409/400/423 pass through; an unclaimed request fails fast with 503 and is retracted only while its request file still exists). Hosted saves are interactive, not durable: a crash mid-save surfaces as a client timeout and the user saves again. Direct service callers (unit tests, in-process server-host producers, the grid patch endpoint, refresh flows) still run locally, mark the first reachable downstream method tier review-needed, and submit the canonical versioned `ArcRhoRefreshDependents` request through `arcrho_dependent_propagation_contract`; the Engine propagation job re-marks the full reachable closure on local disk as its first claimed step, before the walk, and a marking failure never aborts the walk; the client never runs the dependent cascade itself, and there is exactly one cascade implementation — `calculated_dataset_service.recalculate_dependents`, invoked only inside ArcRho Engine or, for server-host in-process producers (ResQ migration, public Python API), under the same reserving-class lease the Engine uses. Submission preflights a fresh Engine heartbeat before anything is written; with no live Engine the save is refused and unsaved work stays in the editor. The hosted-save publisher reuses the workspace root returned by that preflight. Successful dependent-protocol path safety checks are cached by normalized workspace root for 30 s, while an inaccessible root, a failed validation, or a changed workspace root invalidates or bypasses that cache; heartbeat and reserving-class hold probes still run for every save. Requests queue in the `requests/dependent_propagation/` subfolder, are retained until a validated terminal status exists, and concurrent queued requests for one reserving class are drained and merged into one walk at claim time (`merged_into` statuses). A save whose publication revision is unchanged submits no job (`propagation: {status: "unchanged"}`). Failed jobs are not auto-retried: the status file carries the error, downstream stays review-needed, and the next save or manual refresh re-enqueues the walk. Because the locked job is the sole propagation writer, the calculated-dataset open fast path may trust a current sidecar status plus a reserving-class `index.json` whose `folder_signature` matches a fresh folder listing as evidence of currency and skip the deep per-precedent fingerprint walk; a review-needed status, a moved signature, a missing or invalid index, contract drift, or any read doubt must fall back to the unchanged deep validation. Open dataset and method windows watch their object's stat-only fingerprint (`/object_change/fingerprint`) and show a one-time advisory alert — with a Refresh Now action that reloads a clean window in place — when another user or automation rewrites it. The alert must name the writer rather than only report that one exists: after (and only after) the fingerprint moved, the window reads `/object_change/attribution` once for the attribution the write itself recorded — the object's last sidecar audit entry, projected by the canonical `arcrho_api.sidecar_audit_contract` — and says who saved it, or which automation task rewrote it and the account that task ran as. That read is per alert, never per poll, so the steady-state watch stays two stats; an unreadable or unattributed payload falls back to the generic sentence and never turns the advisory alert into an error. The alert must also survive a share that lies about when a file changed: a mapped-drive `os.stat` can be answered from the SMB redirector's cache and report metadata seconds old, so a post-save rebase can baseline on the pre-save stat and then raise the alert for the user's own save. Neither a cache-busting probe write nor an open handle fixes that (a handle would fail the concurrent atomic replace), so the rule is a comparison, not a better read: each window records the `updated_at` of the write it already has in view, and a moved fingerprint whose recorded write is not newer than that stamp is re-baselined silently. Staleness can only ever report an older state than the truth, so only a genuinely newer write can pass that test. The Project Instance dataset-table watch (the timer-polled `/datasets/cached/index-signature`) follows the same rule: it baselines on the `index_signature` the `/datasets/cached` snapshot response itself carries — statted by the process that wrote or validated `index.json`, the Gateway for hosted reads — and ignores a polled signature whose mtime is older than that baseline, so a save, propagation walk, delete, or retarget this app session triggered never raises the `Refresh Table` prompt while a genuinely newer index write always does. A window's own saves must rebase the watch and never trigger the alert, and neither may a propagation job enqueued by the same app instance: the save's dependency-source `cleared` message carries the `propagationJobId`, Project Instance defers the downstream live-preview clear until the job's terminal status so dependents never snap back to stale values, and its propagation-scope broadcasts pause the affected windows' watches until the refreshed values are reloaded. A running walk holds its reserving class against new writes: every propagation-triggering save preflights `require_reserving_class_writable` (live-Engine check plus the canonical `find_reserving_class_propagation_hold` probe) and is refused with `423` while the class's lease heartbeat is fresh (within `DEPENDENT_PROPAGATION_STATUS_STALE_SECONDS`) or a queued request younger than `DEPENDENT_PROPAGATION_QUEUED_STALE_SECONDS` lacks a terminal status; other reserving classes stay writable, an orchestrated multi-save operation (the Excel workbook retarget, itself an Engine-hosted save kind) preflights once, suspends the refusal for its nested saves, and collects their roots through `deferred_save_propagation` into one walk flushed at its end — because it re-saves objects on their owners' behalf, it marks each re-saved DFM output `2` after the save and walks from it, so downstream is flagged even when the publication is unchanged — and the check-then-write gate stays non-atomic with the Engine's queued-request merge as the race backstop. The Engine worker republishes each job's `processing` status on the `DEPENDENT_PROPAGATION_STATUS_HEARTBEAT_SECONDS` cadence even when progress has not advanced, so pollers and the hold both distinguish a live slow walk from a dead worker and a dead worker releases the class and the waiting UI by itself. The saving window shows the plain saving popup (no live per-dataset stream — the Engine-hosted save returns with the walk already finished); on a clean outcome a transient notice inside the saving window lists the exact dataset instances the walk refreshed (`propagation.refreshed_datasets`, auto-dismissing after ~2 s), then only the explicit Save command closes the window (Save As, Sync, and bridge saves never close), and a save whose inline walk reported failures keeps the window open with the dataset table's review-needed flags as the failure surface. Project Instance polls `/dependent_propagation/reserving_class_busy` for the selected class and, while busy, quietly pauses its own class-mutating actions — there is no banner above the dataset table; a blocked action explains itself in the status bar and the live updates stream in the saving window's popup; the 423 refusal is the enforcement, the freeze is UX.

16. Keep the hosted-save HTTP transport an additive transport around rule 15. The local app server must send the exact canonical `ArcRhoHostedSave` request to the machine-wide Gateway; `arcrho_hosted_save_http_contract` owns HTTP authentication, canonical request hashing, configuration, and receipt paths but never owns a second sidecar or method schema, and it must derive its supported save kinds from the canonical `SAVE_JOB_KINDS` registry rather than restating them. Neither the Gateway configuration nor the Gateway itself may carry a second save-kind allowlist; a client routes a kind over HTTP only when `/api/capabilities` advertises it and otherwise keeps that kind on SMB. The shared Gateway configuration owns the canonical `client_url`; when the local credential file is absent, ArcRho startup may probe that URL and atomically enroll the current Windows user, while an existing local file remains authoritative. Failure before enrollment leaves SMB selected, but an uncertain HTTP response after enrollment must retain and retry the same request ID and must never fall back automatically to SMB. The Gateway performs live-Engine/class-hold preflight and all request/status filesystem work on server-local disk, persists a receipt before publication, binds one request ID to one canonical request, and returns the stored outcome on replay. The Engine remains the only save executor, and route response shapes, error codes, method/sidecar payloads, propagation, review status, index behavior, and UI close/dirty semantics remain unchanged. Plain HTTP is permitted only for the explicitly enabled no-IT performance pilot and must be replaced by HTTPS before production rollout.
17. Keep Server-hosted workspace reads an additive transport around the canonical read services. `arcrho_workspace_read_contract` owns the `WORKSPACE_READ_KINDS` registry (read kind → `app_server.services` module, function, and the exact keyword arguments a client may pass), the route path, and request validation; the Gateway executes only a registered kind, imports only the module the registry names, and passes only the registry's arguments, so no second table of reads may exist in the Gateway, a router, or a document. The reads run the unchanged service function — on the server host inside the Gateway when `/api/capabilities` advertises the kind, otherwise locally — so route response shapes, error codes, cache and index behavior, and review semantics are identical on both transports; a hosted service refusal passes through with its own status. Reads keep no receipt and may fall back to the local path after a gateway-layer failure because they are pure functions of the workspace, but a process that runs with `ARCRHO_RUNTIME_SERVER_ROOT` set must never route a read to the gateway. A gateway response carries the server workspace root and the client rebases every server-rooted path onto its own root before returning it; a read that registers per-process state (the dataset handle registry) must adopt it from a remote payload through a `finalize` hook. Machine-local values that are not paths must not travel through this transport. The Gateway binds `acting_identity` around each read so any one-time on-disk upgrade a load performs stamps the opening user.
18. Keep Gateway-hosted Engine calculations an additive transport around the legacy request-file exchange and the unchanged `arcrho_runtime_service` routes. `arcrho_engine_calculation_contract` owns the `ENGINE_CALCULATION_KINDS` registry (Engine function → the exact request-file keys its handler reads, whether a reserving class is named, allowed output variants and operations), the `OPERATION_OPTIONS` table, the server-owned keys a client may never send (`DataPath`, `StatusPath`, `RequestId`, `UserName`), the route path, wait clamping, and request validation; the Gateway executes only a registered function and operation through the one canonical `app_server` executor the module names, derives the output path itself with `set_data_path_like_vba` (or the Temporary view path for the `temporary_view` variant), and for the `exchange` operation publishes into the server-local `requests` root the Engine already watches and waits on local disk, while `dataset_run` / `dataset_precheck` run the unchanged `run_arcrho_tri` / `arcrho_precheck` service functions on the server host — cache validation, exchange, sidecar write, dependent enqueue, index refresh, and lock semantics identical to the local route — and return their responses verbatim. The Engine handler, the request file, the CSV, and its location are unchanged, and Excel, `arcrho_api`, and the migration keep publishing over SMB. The `/arcrho/tri*` and `/arcrho/vec*` routes go through `engine_calculation_service.run_hosted_dataset_operation` and every remaining request site through `run_engine_calculation`; both use the Gateway only when the output CSV is on a network drive, the process is not a server process, and `/api/capabilities` advertises the function (and operation), fall back to the local path only for a gateway-layer failure before the request could have been acted on, and never publish a second request or re-run the route after the Gateway may have accepted one (an exchange reports `timeout` / `gateway_error`, a dataset operation raises `504`). A hosted response has its server paths rebased onto the client root; the exchange client verifies the server-derived output path equals its own and waits for the CSV to become visible on its own drive, and a hosted `dataset_run` registers its `ds_id` handle locally through `dataset_service.register_dataset_handle`.
19. Keep an ArcRho object deletable only once nothing reads it, and keep Server-hosted workspace mutations a separate, idempotent-only transport. `dataset_service.delete_cached_datasets` must resolve the requested datasets' direct sidecar `Dependents` edges before removing any file and, when a dependent outside the same request survives, remove nothing and raise `409` with the structured detail `{error: DELETE_BLOCKED_BY_DEPENDENTS, message, blocked_datasets:[{dataset_name, dependents:[{dataset_name, method_type}]}]}`; the check is whole-request so a refusal is never half-applied, a dependent named in the same request is not a blocker, and only direct dependents are reported because a deeper descendant is reachable only through one of them. The frontend must not pre-check dependents to enable or disable Delete: the server's refusal is the single authority, and Project Instance turns it into a window whose dependent links open that object's own method or dataset window so the input can be cleared there. The delete itself never removes the dependent's reference on the user's behalf. `arcrho_workspace_mutation_contract` owns the `WORKSPACE_MUTATION_KINDS` registry (kind → `app_server.services` module, function, the exact keyword arguments a client may pass, and which of them are name lists), the route path, and request validation; the Gateway executes only a registered kind, imports only the module the registry names, and passes only the registry's arguments, so no second table of mutations may exist in the Gateway, a router, or a document. Only an idempotent operation may be registered — running it twice must leave the end state of running it once — which is what lets this transport, like reads, keep no receipt; anything else belongs on the hosted-save path. Unlike a read, a mutation may fall back to the mapped drive only when the failure proves the server never acted (`GatewayTransportFailure.accepted` false); a timeout or a connection lost after the request was sent raises `504` telling the user to refresh rather than re-running locally, and a process with `ARCRHO_RUNTIME_SERVER_ROOT` set must never route a mutation to the gateway. Both transports must deliver a structured refusal `detail` as the same object, with only its free text redacted for server paths, and a hosted response has its server-rooted paths rebased onto the client root.

20. Keep a dataset-type table change atomic against the reserving classes it reaches, and let the user see that set before it is locked. `POST /dataset_types` classifies the change before writing anything. A change needs the Engine job when a type was renamed or disappeared, when a surviving type's `Data Format`, `Calculated`, `Formula` or `Generated` moved, or when the components some calculated formula *resolves to* changed -- which a newly added name can do to a formula whose text never moved, because a formula is tokenized against the set of known names and this project's names contain operators (`Total - CWOP`). Everything else is written by the app server and confirmed in the response: Category, row order, and in particular **adding an ordinary dataset type, which must stay instant** -- a new type has no instances and no sidecar naming it, so nothing derived from the table moves. Comparing resolved components rather than assuming any new name is dangerous is what keeps the most common edit off the slow path. A rename is a rename, not a removal plus an addition: the grid sends `renames: [{from, to}]` for every Name it edited, the instances of the old type adopt the new name, a plain instance named after the old type that nothing reads is renamed with it, and formulas naming the old type are rewritten -- so a renamed type never leaves its instances behind under a name the table no longer defines. A change that does need the job is first *planned* (`dataset_types_plan_service`, hosted on the Gateway when one is up): without any lock, from the two tables and one `index.json` per reserving class, the planner names the classes holding an instance of a renamed, changed or removed type, of one of their direct precedents, or of anything downstream, with counts and a reason per class, plus a digest of the saved table. The route answers `applied: "plan"` and the grid shows that list in a confirmation dialog; only a second POST carrying the plan submits the job, and a plan naming no class with no rename is submitted at once. The submitted form is the durable Engine job owned by `arcrho_dataset_types_change_contract`: submission preflights a live Engine, no project-scope job already running, no reserving class of the project still being walked (`find_any_reserving_class_propagation_hold`), and no source refresh holding the project, then publishes the queued status before the request and returns a job id the client polls at `GET /dataset_types/change_job/status`. The Engine claims the project-scope lease owned by `arcrho_dependent_propagation_contract` -- not a per-class lease, because the table belongs to no single class -- re-checks that no class walk was claimed in the submission gap, and **recomputes the plan under that lease**: unless it matches the confirmed one (`plans_match`: same digest, same classes, same counts) the job fails with "the project changed since you reviewed this change" and nothing is written, because the classes the user agreed to lock must be the classes that are locked, never a silently wider set. A change that removes a dataset type is then refused before anything is written when any instance of a departing type is still read by a dataset or method that is not itself departing: deleting the type deletes the definition its instances are described by, which is rule 19's principle applied one level up. The refusal names the type, the instance and its readers, and states that nothing was saved; an instance nothing reads is not a blocker. Only then does the job write the table, append the audit entry, **narrow the lease to the affected classes** (`narrow_project_scope_lease`) and rebuild those classes only. The whole project is held only from the claim until the table is written; from then on a class the plan did not name can only gain instances of the new names, so holding it protects nothing. While the lease is fresh `find_reserving_class_propagation_hold` reports `{reason: "project"}` for every class of the project, then for the named classes only, so every save into a held class meets the existing `423`; `find_project_scope_propagation_hold` keeps reporting the job, so neither a second project-wide job nor a source refresh can be queued beside it; a source refresh submitted against a held project is refused the same way. Both producers write the table through one function (`dataset_types_service.apply_dataset_types_rows`), which owns normalization, formula validation, the derived `Source`/`Generated` columns and the persisted text, so a table written by the app server and one written by the Engine are the same document for the same rows; the contract module validates only the transport shape of a row. A partially failed rebuild is a terminal `error` whose message states that the table was saved, because it was. The job's progress is counted in dataset instances, then in the reserving classes the change makes the walk revisit, so a caller's bar measures work rather than stages; the denominator grows once, when the rebuild has listed the project, and the count never moves backwards. The client must never present an unanswered save as saved: the shared auto-save scheduler releases its single-flight slot on a watchdog and reports it, and a running job blocks Project Settings behind the shared progress popup -- which shows a determinate bar whenever a caller supplies a total -- rather than reporting itself in a status line the user can miss.
