2026-08-06 investigation of "Saving a DFM took a long time on a Client PC" (still >60s on client 1.2.1):

- `save_dfm_method` (frontend/app_server/services/dfm_service.py) calls `calculated_dataset_service.recalculate_dependents(..., rebuild_index=True)` unconditionally after every save; the UI awaits the full response. Measured on a sandbox copy of `NJ_Annual_Prod_202605_Fake` / HOL class: save core ≈30 network file ops; the propagation walk + index rebuild ≈130 more ops even when every downstream method is blocked/no-op (~80% of the request). Real cascades also rewrite CSVs/sidecars and can trigger ArcRho Engine materialization (`result_selection_service._materialize_engine_source` → `run_arcrho_tri`, 15s budget) detected by client-side SMB polling — the minute-scale contributor.
- Profiling harness technique: copy workspace `config/` + project root JSONs + ArcRhoHeaders CSVs + one reserving-class folder to a SHORT path (MAX_PATH: scratchpad temp prefix is too long — use a repo-local `.tmp_*` folder, delete after), set `ARCRHO_SERVER_ROOT` env to the sandbox, monkeypatch `builtins.open`/`os.scandir`/`os.stat`/`os.replace` for counts + injected latency, and wrap service functions to attribute ops per phase. Import `pathlib` BEFORE patching `os.stat` (its class body binds `os.stat`; a Python-function patch gets method-bound and breaks). Fake-project caveats: MP+PIP class lacks raw triangle caches; most fake datasets are "needs review" so downstream recalcs short-circuit — full-cascade cost must be reasoned statically.
- Offload feasibility: the Bridge already bundles `frontend/app_server` (server-components/src/arcrho_bridge/bundled_sources.py) and runs on the server host where `E:\ArcRho Server` is local; project duplication (`arcrho_project_duplication_contract.py`, 202-and-poll at 750ms) is the durable-job template. Blockers to design around: `reserving_class_io_lock`/`sidecar_write_lock` are per-process `threading.RLock`s (not cross-machine; only `dataset_index_contract.index_update_lock` spans machines via msvcrt byte-range lock); Bridge worker only runs while a ResQ Enterprise window is open; orchestrator GCs `requests/` files older than 5 min (use a subfolder queue).
- Version caveat: the 2026-08-05 scan fix (commit 41ac3fa) was still in `frontend/changes/unreleased/` with package.json at 1.2.0 while the client reported "1.2.1" — verify whether a client build actually contains a fix before re-diagnosing.
- The approved implementation plan (Engine-hosted propagation job, owner-confirmed decisions incl. allow-save-during-job, in-process+lease for server-host producers, no auto-retry, save blocked when no Engine heartbeat) is at `docs/plans/engine_dependent_propagation_plan.md`.

- Phase-2 follow-up (2026-08-07, user-reported C22/C61 live-preview conflict in COL fake project, uncommitted): the async Engine job made source-save preview teardown race the refresh — downstream windows snapped to stale values, then the change alert popped. Fix (frontend-only, no Engine/Bridge rebuild needed): saves attach `propagationJobId` to `arcrho:dependency-source-cleared` (DFM via `dfm_state.setPendingDfmPropagationJobId`, RS via `state.pendingPropagationJobId`, BS via module var); PI (`project_instance_messages.deferDependencyClearUntilPropagation`) defers the relay + calculated-preview fan-out clear until `waitForDependentPropagationOutcome` (never-throwing wrapper in `dependent_propagation_job.js`) and brackets it with `arcrho:dependent-propagation-started`/`-finished` scope broadcasts; pages pause their watches via `wireSamePropagationScopePause` (failsafe resume timer); the alert now uses `showObjectUpdatedAlert` with a "Refresh Now" action (message_box gained an `actions` param, resolves the clicked action id) that reloads clean windows in place and blocks dirty ones with a status warning. PI is the only preview message router (source windows post to parent; shell does not relay dependency-source messages), so the deferral there covers all consumers.
- Second regression round (2026-08-07, uncommitted): the deferral alone was NOT enough — DFM saves fire TWO clean transitions (`applyDfmMethodPayload(markClean:true)` then `markDfmClean({force:true})` at dfm_persistence.js ~1688; `force` re-dispatches the event even when already clean), each posting a dependency-source-cleared; only the first carries the job id (consume-once), so PI relayed the job-less duplicate immediately → downstream reloaded pre-walk stale values and the later deferred relay found an empty preview-target map (no second reload) → window stuck on old values. Fix: PI (`deferDependencyClearUntilPropagation`) keeps a `pendingDependencyClearSourceCounts` map keyed by `dependencySourceKey` and swallows job-less cleared messages while that source has a deferral pending. Owner also removed the "Dependent updates did not complete..." status-bar warning: `trackSavePropagation` now ends failed jobs quietly ("Dependent updates finished at ...", info tone) and fires `onComplete(null)` on failure too so the PI table refreshes and its review-needed flags are the sole failure surface.
