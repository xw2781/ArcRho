What changed and why (informed by the 15 production rules)

  1. 1Auto-generated names. Production names have typos (“Exculde”) and drift from content (a rule named “keep BIx51+UMBIx51” whose trigger is BI+PIP). If the name is left blank, the app derives one from the rule itself (shown as the AUTO placeholder — clear the field to see it live); typing anything overrides it.
  2. 2Dataset type is multi-select. Production has near-duplicate rules that differ only by dataset type (e.g. “keep HOP” exists separately for Earned exposure and Earned premium). Letting one rule target several dataset types removes that duplication. This is the one proposal that needs a small schema change (target.source_measures as a list, with single-value kept readable for back-compat).
  3. 3Then = one row-level clause. “Row filter” and “Action” merge: the member list and raw-row filters are ANDed row constraints, so they read as one sentence. The saved JSON stays the same — the condition on the action field maps to action.members, the rest map to row_conditions.
  4. 4One operator, token values. Production mixes equals with single strings and in with lists for the same intent — evidence the two operators should collapse into one tokenized “is (any of)” input. One token = equals, several = any-of; save can normalize to a single canonical operator.
  5. 5Always-visible plain-English summary pinned above the buttons, restating the whole rule live as you edit.
  6. 6List grouped by dataset type with sentence summaries. With 15 rules the flat 6-column table is hard to scan; 13 of 15 rules follow the same “substitute coverage” shape (request X → keep only Y), which a compact “when → then” sentence shows at a glance. Colored KEEP/EXCLUDE badges make the two NJ exclusion rules stand out. Amber chips flag lint findings: near-duplicates across dataset types and name/content drift.
  7. 8Dataset-aware value vocabularies. The merged source CSV is an outer join of separate tables, so a column like IBNRCAT mixes aggregation levels: atomic coverages (BI, PD, PIP…) only exist on Earned premium/exposure and loss rows, while pre-aggregated values (BI Total, PD+UMPD, BIx51+UMBIx51, CMPxCAT…) only exist on Remaining budget rows. Value suggestions therefore filter by the selected dataset type(s), and chips are validated against that vocabulary: amber = only valid for some selected dataset types, red = never present (the condition can never match). Try adding “Remaining budget premium” to the dataset chips to see the BIR51/UMBIR51 tokens flag themselves. Validation should warn, not block — values may legitimately appear in a future data refresh.
  8. 7“Which rules fire?” tracer. With this many keep-only remaps on overlapping coverage lists (e.g. TOTAL PA appears in several rules), the key question when debugging is “what happens to this request?”. Pick a dataset type + coverage + state and the panel lists the rules that would fire. Try Earned exposure / TOTAL PA, then Earned premium / TOTAL PA.
